# Oracle 19c 백업과 복구 실습: 장애를 일부러 만들고 되살렸다

> 백업 파일이 있다는 것과 복구할 수 있다는 것은 다른 말이다. 앞의 것은 누구나 말할 수 있고, 뒤의 것은 해 본 사람만 말할 수 있다.

**강영수**, DBA 포트폴리오, 2026-10-31~11-01

---

## 1. 무엇을 했나

직접 설치한 Oracle 19c 서버에서 RMAN(Recovery Manager, Oracle 백업 복구 도구)으로 백업 체계를 만들었다. 그 위에서 장애 다섯 가지를 일부러 만들고, 각각 복구에 걸린 시간과 잃은 데이터를 쟀다.

서버는 VirtualBox VM 1대다. OS 설치부터 DB 생성, 자동 기동까지 손으로 구축했고, 같은 구성을 Ansible로 자동화한 버전과 점검 스크립트 17항목으로 비교했다. 이 실습은 그 서버를 운영하는 단계에 해당한다.

| 항목 | 내용 |
|---|---|
| DB | Oracle 19c EE 19.3, CDB 1개와 PDB 1개, ARCHIVELOG 모드 |
| OS | Oracle Linux 8.10, VM 메모리 4GB |
| 디스크 | 데이터용 `/oradata` 100GB와 백업용 `/backup` 100GB를 분리 |
| 기간 | 2일, 실작업 약 6시간 |

---

## 2. 백업 설계

| 항목 | 설정 | 이유 |
|---|---|---|
| 방식 | 증분 백업. 일요일 Level 0(전체), 월~토 Level 1(변경분) | 매일 전체를 받으면 시간과 공간이 낭비된다. Level 1은 40초 만에 끝났다 |
| 압축 | 기본 압축 | 4.7GB 데이터가 660MB가 됐다 |
| 보관 | 최근 7일 안 어느 시점으로든 복구 | 오래된 백업은 스크립트가 자동으로 지운다 |
| 컨트롤 파일 | 자동 백업 켬 | 구조가 바뀔 때마다 새로 생겼고, 시나리오 C와 D에서 그 최신본으로 복원했다 |
| 검증 | `RESTORE DATABASE VALIDATE` | 백업을 실제로 읽을 수 있는지 미리 확인한다 |
| 자동화 | 셸 스크립트와 cron, 실패 시 한 줄 알림 | 사람이 잊어도 백업은 돈다 |
| 디스크 분리 | 데이터와 백업, 아카이브 로그를 다른 디스크에 둠 | 데이터 디스크가 통째로 망가져도 백업은 남는다. 시나리오 D가 이 설계를 시험했다 |

## 3. 장애 실습 결과

| 시나리오 | 만든 장애 | 복구 방법 | RTO(복구 시간) | RPO(잃은 데이터) |
|---|---|---|---|---|
| A-1 | 조건을 잘못 쓴 DELETE 1000행 | Flashback Query로 과거 시점을 읽어 다시 넣음 | 5분 이내 | 0 |
| A-2 | 테이블 DROP | 휴지통에서 Flashback Table, 인덱스와 제약 조건 이름 복원 | 1분 이내 | 0 |
| B | 운영 중 데이터 파일 1개 삭제 | 해당 테이블스페이스만 내리고 복원과 복구, DB는 계속 운영 | 약 6분 | 0 |
| C | 컨트롤 파일 2개 모두 삭제 | 자동 백업에서 컨트롤 파일 복원, 남은 리두 로그 적용 | 약 3분 | 0 |
| D | 데이터 디스크 전체 삭제 | 컨트롤 파일과 DB 전체 복원, 마지막 아카이브 로그까지 복구 | 약 5분 | 커밋 1건 |

다섯 번 모두 복구했다. 실습이 끝난 뒤에도 서버 점검 스크립트 17항목이 모두 통과했다.

시나리오마다 "백업 뒤에 넣은 행"을 표시로 남겼다. 복구 뒤 그 행이 있는지로 어느 시점까지 되살아났는지 판단했다. D에서는 아카이브 로그에 들어간 행은 살아남았고, 온라인 리두 로그에만 있던 행 1건은 사라졌다. 예상과 정확히 같았다.

## 4. 직접 해 보고 알게 된 것

**C와 D의 차이는 온라인 리두 로그 하나였다.** 컨트롤 파일만 잃은 C는 남은 리두 로그 덕분에 마지막 커밋까지 되살렸다. 리두 로그까지 잃은 D는 마지막 아카이브 로그까지만 살렸다. 리두 로그를 다른 디스크에 다중화하는 이유를 숫자로 확인했다.

**설정 하나가 복원 경로를 바꿨다.** 이미 백업한 파일을 다시 받지 않는 BACKUP OPTIMIZATION을 켜 두었다. 그 결과 D에서 읽기 전용 PDB$SEED는 하루 전 세대의 백업에서 복원됐다. RMAN은 RESETLOGS로 세대가 바뀐 뒤에도 알맞은 백업을 스스로 골랐다.

**테이블을 되살려도 끝이 아니었다.** Flashback Table은 테이블 이름만 되돌렸다. 인덱스와 기본 키 제약 조건은 휴지통 이름(`BIN$…`)으로 남아 직접 원래 이름으로 바꿨다. 복구 뒤 확인 목록에 넣을 항목이다.

**화면이 멈춰도 로그는 거짓말하지 않았다.** 설치 단계에서 DB 생성 도구 화면이 8%에서 1시간 넘게 멈췄다. 화면 대신 생성 로그와 alert log, DB의 실제 상태를 차례로 확인해 생성이 이미 끝났다는 것을 판단했다. 같은 습관이 이번 실습에서도 장애를 확인하고 복구 결과를 검증하는 데 쓰였다.

## 5. 다음에 개선할 것

| 개선 | 기대 효과 |
|---|---|
| 온라인 리두 로그를 다른 디스크에 다중화 | 시나리오 D에서도 손실 0 |
| 백업을 다른 서버나 저장소로 복사 | 서버 자체를 잃어도 복구 가능 |
| 아카이브 주기 단축(`archive_lag_target`) | D와 같은 상황에서 잃는 범위 축소 |
| 분기마다 복구 리허설 | 백업과 절차가 실제로 통하는지 정기 확인 |
| 패치 적용(19.3에서 19.25) | Oracle Linux 8과의 지원 조합 확보. 패치 파일은 지원 계약 계정이 필요하다 |
